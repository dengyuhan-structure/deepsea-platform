# 🔴 推送并核实（用这个，别再用 git fetch + 本地比对）

## 为什么需要这个脚本

**2026-10-07 踩的坑**：我几次说"已推送成功"，其实有两个提交根本没上去。

原因是我的核实方法是错的：

```powershell
git fetch origin          # ← 这一步可能静默失败（代理断了）
git rev-parse main        # 本地分支
git rev-parse origin/main # ← 本地缓存的"远端"引用，fetch 失败时是旧值
# 两者相等 → 误判为"已同步"
```

**`git fetch` 失败不会报错，只会让本地的 `origin/main` 保持旧值。**
于是"本地 == origin/main"这个判断就**骗了自己**。

**更糟的是**：当时我根本不在 `main` 分支上（在 `struct` 分支），
所以 `git push origin main` 推的是**旧的 main**，而我的新提交在 `struct` 上 —— 一条都没上去。

---

## 正确做法

```powershell
# 用 ls-remote 直接问远端，不信本地缓存
$remote = git ls-remote origin main | ForEach-Object { $_.Split()[0] }
$local  = git rev-parse HEAD
if ($remote -eq $local) { "✅ 真的同步了" } else { "❌ 没上去" }
```

跑 `scripts/推送到GitHub.bat`（或下面的命令）即可，它会：
1. 先确认**当前在 main 分支**（不在就警告）
2. 提交
3. 推送
4. **用 `ls-remote` 实查远端**，不一致就明确报错

---

## 三条纪律

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | **提交前先看当前分支** | 今天就是站在 `struct` 上往 `main` 推，白推 |
| 2 | **核实要用 `ls-remote`，不要用 `git fetch` + 本地比对** | fetch 静默失败会让判断骗人 |
| 3 | **推送失败要当回事，不能"看着像成功了"就过** | 今天连着两次误判 |

> **一句话**：**别信本地缓存，直接问远端。**
